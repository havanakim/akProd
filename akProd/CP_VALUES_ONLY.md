# CP_mono · CP_Colored 수치 전용 등록 (2026-11-17)

v1.1.3 저장 상세 화면은 반복된 구역별 표를 하나로 합친다.
CP_Colored는 단계별 행/압력·속도·시간·위치 열, CP_mono는 항목별 행/5~1단 열로 표시한다.
상하 패딩·글꼴 기본 여백을 줄이고 목록/메뉴 이동 버튼을 가로 한 줄로 배치한다.
단위와 null의 — 표시는 유지한다.

v1.1.0부터 두 등록 화면 상단의 조회·촬영·사진 선택·선택 취소 버튼은 가로 2개씩 2줄로 배치한다.

서버 등록시각 REGISTERED_AT은 GETDATE()로 DB 서버의 로컬 시간을 저장한다.
기존 UTC 기록은 변환하지 않는다. 새 APK가 등록시각을 명시하므로 기존 DB 기본값 변경은 필요 없다.

두 메뉴에서 신규 사진 DB 저장을 제거했다. 사진 촬영·선택·OCR·0 글꼴 학습은 유지한다.

사진 목록에서 취소할 사진을 고르고 `선택 사진 취소`를 누르면 추가된 사진을 제외할 수 있다.
확인창에서 취소 여부를 선택하며, 입력된 수치는 유지하고 입력값 확인 체크를 해제한다.
마지막 사진을 제외하면 미리보기와 숫자 영역 표시를 비운다. 갤러리 원본은 삭제하지 않는다.
등록 진행 중이거나 결과 미확인·완료 상태인 요청의 사진은 변경할 수 없다.

## 0과 빈 항목 처리

`000`, `000.0` 등은 숫자 0으로 인식·검증한다. OCR 표 매핑 결과는 기존처럼 `0`으로 정규화하며,
직접 입력한 숫자는 표시 자릿수(예: `000.0`)를 보존해 저장한다.
빈 문자열·공백·누락 항목은 FIELDS 안에 실제 JSON null로 기록한다(예: `"IP4": null`).
문자열 `"null"`이나 빈 문자열로 보내지 않으며, 0을 null로 바꾸지 않는다.
CP_mono는 선택 화면에 해당하는 항목만 저장하고 다른 화면 항목은 추가하지 않는다.
잘못된 숫자 문자열은 계속 등록을 막는다. 조회에서 null은 `—`로 표시한다.
자동 인식 실패로 남은 빈칸도 null이 되므로 사용자는 등록 전 빈 항목을 확인해야 한다.
이 변경에 추가 DB 스키마 변경은 필요 없다(사진 저장 제거용 cp-values-only.sql은 여전히 필요).

사진 없이 직접 입력한 값도 확인 체크 후 등록할 수 있다. 이 경우 기준시각은 등록 준비 시각이다.
공정관리일지의 사진 저장에는 영향을 주지 않는다.

## 배포 순서

1. 앱이 접속하는 DB_NAME 데이터베이스에서 `scripts/cp-values-only.sql`을 한 번 실행한다.
2. `app/build/outputs/apk/debug/app-debug.apk`를 설치한다.
3. CP_mono·CP_Colored에서 수치를 등록하고 저장자료 조회로 확인한다.

기존 테이블은 PHOTO_COUNT가 1 이상이어야 한다는 제약이 있어 0을 허용해야 한다.
전환 스크립트는 두 테이블의 사진 수 제약만 0~5로 변경한다. 기존 입력값과 사진은 삭제하지 않는다.
신규 설치용 cp14-schema.sql·cp3-schema.sql·cp-menu-schema.sql도 0을 허용한다.
서버에 이 스크립트를 실행하지 않은 상태에서는 제약조건 오류로 신규 등록이 실패할 수 있다.

## 저장 동작

- CP_mono·CP_Colored 본문 테이블에 수치 JSON·작업자·시각·요청 ID·내용 해시를 저장한다.
- 신규 자료는 PHOTO_COUNT=0이며, 사진 테이블 INSERT/UPDATE나 사진 파일 읽기를 수행하지 않는다.
- 저장 해시는 수치 요청만으로 생성한다. 기존에 사진과 함께 저장된 동일 요청은 작업자·설비·시각·수치가 같으면 사진 재전송 없이 재확인한다.
- 기존 자료의 사진은 계속 조회할 수 있다. 신규 자료에는 저장 사진 보기 버튼이 없다.
- 미확인 요청의 OCR 사진 경로와 입력 초안은 기존처럼 기기에 남겨 재시도에 사용한다.
- CP DB 저장 전용 연결은 prepareSQL=2(sp_executesql)와 packetSize=512를 사용하며, 잠금 대기 10초·쿼리별 제한시간을 설정한다.
- 등록 버튼 아래에 진행 단계와 DB 세션을 표시한다. UI 대기 35초 후에는 같은 요청으로 재확인할 수 있다.
- 시간 초과가 발생해도 서버 롤백을 단정하지 않고 같은 요청 ID를 유지한다.

## 검증

`assembleDebug`, `testDebugUnitTest` 성공. JUnit 21개 통과(기존 16개 + 저장 검증 5개).
신규 검증은 두 메뉴의 사진 없는 등록, 동일 요청 중복 방지, 기존 사진 요청 재확인,
다른 작업자·변경된 내용 거부, 실패 시 롤백 및 시간 초과 단계·세션 표시를 포함한다.
저장 검증은 JDBC 대역으로 실행했으며 실제 SQL Server와 실기기 저장 성공은 미검증이다.
서버 제약조건 전환 스크립트도 아직 실제 DB에 실행하지 않았다.
