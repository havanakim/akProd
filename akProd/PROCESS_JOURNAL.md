# 공정관리일지 사진 등록·조회

메뉴: **등록 → 공정관리일지 · 사진 등록**, **조회 → 공정관리일지 조회**.
첨부 일지와 같은 ACN-A-0602-2-5 양식 전용입니다. 기존 CP_Colored / CP_mono 기능은 유지합니다.

## 최초 DB 준비

SQL Server Management Studio에서 `local.properties`의 **DB_NAME** 데이터베이스를 선택하여
[scripts/process-journal-schema.sql](scripts/process-journal-schema.sql)을 실행합니다.
신규 테이블 `dbo.AKPROD_PROCESS_JOURNAL`과 검색 인덱스만 생성합니다.
이번 구현 작업에서는 실제 DB 테이블 생성이나 일지 데이터 등록을 실행하지 않았습니다.
기존 로그인 DB는 `DB_AUTH_NAME`, 일지 저장 DB는 `DB_NAME`을 사용합니다.

## 등록 순서

1. 로그인 후 **공정관리일지 · 사진 등록**을 엽니다.
2. 일지 한 장을 정면에서 촬영하거나 사진을 선택합니다.
3. **표 전체 영역 선택**을 누릅니다. 사진에서 일자/금형번호 행의 왼쪽 위부터
   맨 아래 습도/온도 행의 오른쪽 아래까지 외곽 테두리를 드래그합니다.
   제목, M/C NO, 결재란은 영역에서 제외합니다.
4. **표 전체 OCR / 빈 항목 자동 채움**을 누릅니다. 양식의 고정 좌표 안에서 단일 숫자로
   읽힌 후보만 빈 항목에 입력하며, 기존 수동 입력은 덮어쓰지 않습니다.
5. 구역 목록에서 기본정보·상단 조건·각 근의 사출·계량·비고를 차례로 확인합니다.
   **설비번호와 일자(yyyy-MM-dd)는 반드시 입력**합니다.
6. 잘못 읽힌 항목은 직접 수정하거나 항목 선택 → 사진의 값 부분 드래그 →
   **선택 항목 영역 OCR** → 후보를 수정하고 적용합니다.
7. 모든 구역을 사진과 대조한 후 확인 체크 → **DB 저장**을 누릅니다.
8. 저장 후 DB의 상세 조회 화면이 열립니다.

## 인식 범위와 주의점

- 전체 입력은 208항목: 기본정보 7, 상단 시간별 조건 72, 각 근별 43 × 3입니다.
- 상단 최초 기록과 1·2·3근, 사출 위치/압력/시간/속도, 계량 위치/속도/배압,
  로봇 체류시간·원료·잔량거리·특이사항·습도·온도를 분리합니다.
- 조 이름 및 수정된 시간/조 표기는 상단 각 행의 `시간/조 표기`에 직접 기록합니다.
- 날짜·설비번호·텍스트 기본정보·비고·사출시간 행·합쳐 적힌 IF1/IF0는 전체 OCR 자동 채움에서 제외합니다.
  항목별 영역 OCR 또는 직접 입력으로 보완합니다.
- 고정 좌표 기반이므로 종이의 기울기·원근·양식 차이로 다른 칸 숫자가 들어갈 수 있습니다.
  손글씨 자동 인식의 정확도는 보장되지 않습니다. 원본 대조 확인 후 저장하는 보조 입력 방식입니다.
- 숫자 8을 임의로 0으로 바꾸지 않습니다. 빈칸은 빈 문자열, 숫자 0은 `0`,
  사선 표시를 보존할 때는 `/`를 입력합니다. 숫자 칸의 `?` 등은 저장 전 수정해야 합니다.
- 사진은 방향 보정과 해상도/용량 조정 후 JPEG로 보관합니다(최대 8 MB).
  첨부 파일의 원래 바이트와 동일한 보관본은 아닙니다.
- 작성 중 입력과 사진 경로는 사용자별로 기기에 보관합니다. 새 사진을 선택해도 기존 입력은 유지되므로
  다른 일지는 **새 일지 작성**으로 시작하세요.

## 저장과 재시도

사진, OCR 원문, 확인한 항목 JSON, 일지 일자, 설비번호, 작업자, 촬영/불러오기 시각을 한 행에 저장합니다.
요청 UUID와 SHA-256으로 같은 저장 요청을 재확인하며, 트랜잭션으로 저장합니다.
통신 오류 뒤에는 입력을 잠그고 **동일 요청 결과 재확인**을 제공합니다.
저장 결과가 불확실한 상태에서는 새 요청을 만들지 않습니다.
DB 일시 오류로 표시된 경우 DB 테이블/네트워크를 확인하고 같은 버튼으로 재시도합니다.

## 조회

- 시작일·종료일은 촬영일이 아닌 **일지 일자** 기준이며 양 끝 날짜를 포함합니다.
- 설비번호는 빈칸이면 전체, 입력하면 정확히 일치하는 번호만 검색합니다.
- 로그인한 본인의 저장자료만 20건씩 조회합니다.
- 상세에서 사진, 모든 항목과 미기재 값, OCR 원문을 확인합니다.
- 새로 저장한 건은 검색 기간과 관계없이 요청 ID로 상세를 바로 엽니다.

## SQL 조회 예

```sql
SELECT WORK_DATE, MACHINE_NO, USER_ID,
       JSON_VALUE(VALUES_JSON, '$.FIELDS.S1_IP5') AS SHIFT1_IP5,
       JSON_VALUE(VALUES_JSON, '$.FIELDS.S2_S1') AS SHIFT2_METERING_S1,
       JSON_VALUE(VALUES_JSON, '$.FIELDS.S3_NOTE') AS SHIFT3_NOTE
FROM dbo.AKPROD_PROCESS_JOURNAL
ORDER BY WORK_DATE DESC, CREATED_AT DESC;
```

## 검증

양식의 키 중복, 각 근별 항목 수, 좌표 범위, 빈칸/0 구분, 단일 숫자 후보,
여러 숫자 혼합 방지, IF1/IF0 자동 채움 제외 및 날짜 유효성 검증을 실행했습니다.
실제 손글씨 사진 OCR 정확도, 단말 조작 및 실제 DB 저장/조회는 현장 검증이 필요합니다.

## 입력·저장 화면 개선

- 사진 확대: 핀치 확대, 드래그 이동, 두 번 누르면 전체 보기. 조회 사진에도 적용합니다.
- 구역별 입력 수와 자동 채움 수 표시, 이전/다음 구역 이동, 구역별 현황 바로가기.
- 자동 OCR 입력은 주황색 제목으로 표시하며 직접 수정하면 표시를 해제합니다.
- 자동 채움값만 지우기는 직접 수정한 값을 보존합니다.
- 날짜 달력 선택, 잘못 입력한 항목에 오류 표시, 첫 오류 구역으로 이동.
- 조회 상세는 구역별 펼치기/접기와 미기재 숨기기를 제공합니다.
- 초안은 편집 후 자동 보관하며 선택 구역과 자동 채움 표시도 복원합니다.
- DB 저장 전 필수 재시도 정보의 디스크 쓰기는 IO 스레드에서 완료합니다.
- 저장 버튼 아래에 진행 표시와 단계/경과시간을 표시합니다.
- DB 응답 대기는 35초로 제한합니다. 대기 종료는 서버 취소/롤백을 뜻하지 않습니다.
  입력을 보관하고 같은 요청으로 재확인합니다. 이미 실행 중인 동일 요청은 중복 실행하지 않습니다.
- 저장 중에도 메뉴로 나갈 수 있습니다. 해당 요청은 백그라운드에서 계속 처리될 수 있습니다.
- DB 잠금 대기는 10초, 요청 확인 쿼리는 15초, 저장 쿼리는 20초로 제한합니다.
- 테이블 미생성 시 process-journal-schema.sql 적용 안내를 표시합니다.

현재 변경은 소스 컴파일과 검증 코드로 확인했습니다. 실제 단말의 멈춤 현상 해소 및 DB 연결 성공은
새 APK로 빌드·설치하여 확인해야 합니다.

## 35초 응답 시간 초과 시 연결 점검

등록 화면 하단의 **DB 연결 점검 (테이블·권한)**을 실행합니다.
이 점검은 저장 요청과 별도 스레드로 실행하며 DB 데이터는 수정하지 않습니다.
TCP 접속 → JDBC 로그인 → 현재 DB → 일지 테이블 → SELECT/INSERT 권한 순서로 결과를 표시합니다.
문제가 계속되면 해당 결과의 실패 단계와 SQL 오류 번호를 확인합니다.
시간 초과 메시지에도 마지막 저장 단계를 표시합니다.
Android 클래스/API 오류 역시 저장 완료 대기만 남기지 않고 오류로 반환하도록 보완했습니다.

## INSERT 단계 사진 전송 보완

일지 INSERT에서 큰 사진을 jTDS 바이너리 파라미터 한 개로 보내던 경로를 변경했습니다.
사진 바이트를 신뢰 가능한 16진수 리터럴로 변환해 64KB 단위로 같은 트랜잭션 안에서 저장합니다.
전송 단계에 KB 진행률을 표시하며 최종 DATALENGTH를 원본 바이트 수와 비교한 후 커밋합니다.
오류 시 본문과 사진 조각 전체를 롤백합니다. 기존 테이블 구조 변경은 없습니다.
신규 촬영/선택 사진은 최대 1.5MB로 최적화합니다. 기존 미확인 요청의 최대 8MB 사진은
원래 바이트와 요청 해시를 유지하여 재확인할 수 있습니다.
첫 64KB INSERT에서도 계속 대기한다면 scripts/process-journal-lock-diagnostic.sql로
테이블 트리거 및 서버 잠금/대기 상태를 확인해야 합니다.
실제 DB에서의 저장 성공은 확인하지 못했으며 사진 전송 처리 보완과 컴파일/바이트 재구성 검증을 수행했습니다.

## Read timed out 추가 진단

일지 저장 연결에만 jTDS prepareSQL=0을 적용하여 서버 sp_prepare/sp_execute 준비 경로를 사용하지 않습니다.
PreparedStatement의 값 바인딩은 유지됩니다. 로그인 및 기존 CP 연결 설정은 그대로입니다.
저장 오류에는 SQL 오류 코드/상태, 마지막 단계, DB 세션 번호를 포함합니다.
DB 연결 점검에는 akProd-Journal 저장 세션의 wait_type/차단 세션 및 활성 트리거 확인을 추가했습니다.
서버 DMV 조회 권한이 없으면 해당 항목만 조회 불가로 표시합니다.
계속 실패하는 경우 앱에서 저장하는 동안 SSMS에서 process-journal-lock-diagnostic.sql을 실행하여
서버 대기 종류와 blocking_session_id를 확인해야 합니다. 이 스크립트는 세션 종료나 데이터 변경을 하지 않습니다.
prepareSQL 변경으로 실제 저장 문제가 해결되는지는 단말에서 확인이 필요합니다.

## 시간 초과 요청 재대기 및 서버 추적 권한 보완

이전 버전은 실행 중인 요청 Future를 항상 재사용하여, JDBC 정리 작업이 멈춘 경우 재확인도
새 DB 접속 없이 같은 작업을 계속 기다릴 수 있었습니다. 시간 초과된 작업은 새 연결에서 같은 요청 ID로
재확인하도록 변경했습니다. 평상시 실행 중 요청과 완료 결과는 계속 공유합니다.
동시 JDBC 작업은 최대 2개로 제한하며 요청 ID/내용 해시/트랜잭션 검사는 유지합니다.

서버 추적은 VIEW SERVER STATE 권한을 먼저 검사합니다. 이 권한이 없으면 다른 세션이
관찰되지 않는 것을 앱 접속 부재로 해석할 수 없습니다. 프로그램 이름 필터도 제거하고
전체 사용자 세션의 요약과 실행/잠금 상태를 수집하도록 보완했습니다.

## 저장 실패한 현재 항목 초기화

등록 화면 하단의 **현재 항목 삭제 후 새 등록**에서 확인하면 현재 입력/사진 선택/자동 입력 표시/
미확인 요청 초안/오류 메시지를 초기화하고 새 요청 ID로 입력을 시작합니다.
저장 결과 미확인 상태에서도 응답 대기가 끝난 뒤 사용할 수 있습니다.
이 동작은 기기의 현재 작성 내용을 초기화하며 DB에 이미 저장됐거나 처리 중인 요청을 삭제/취소하지 않습니다.
